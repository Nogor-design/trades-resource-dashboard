# Trades Resource Dashboard: Next Development Plan

## Product Direction

The next stages should shift the prototype from a guided demo into a customer-centered hosted workflow. The customer should be able to upload their own data, review what the system understood, use the dashboard safely during a remote session, then reset the environment so one customer's private data cannot leak into the next customer's session.

The current app already has useful foundations:

- `app.py` has a `Client Demo Mode` / `Full Prototype Mode` switch.
- `src/customer_imports.py` already normalizes customer-provided roster, candidate, test, and intake files.
- `Data / Admin` already shows staged customer import previews.
- `.gitignore` already excludes customer spreadsheet/PDF/CSV source files.
- The tracked demo CSVs remain useful as the safe fallback dataset.

## Guiding Principles

1. Customer data is private by default.
2. Raw uploads, normalized working tables, and demo data must be physically and logically separate.
3. Every hosted session needs a visible active-customer/session identity.
4. Reset must clear uploaded files, derived tables, caches, session-state notes, simulated messages, and any temporary exports.
5. The app should always have a known-safe fallback: demo mode with generated demo data.
6. Imports should be staged and reviewed before they become the live dashboard feed.
7. The first production-ish version should favor simple, auditable CSV/file storage before adding a database.

## Stage 0: Privacy And Repo Hygiene

Goal: make sure the project is safe before improving remote upload.

Implementation targets:

- Keep generated demo CSVs under `data/`.
- Move customer raw files out of `data/` in the running app design. Use a future ignored directory such as `runtime_uploads/{session_id}/raw/`.
- Add ignored runtime paths:
  - `runtime_uploads/`
  - `runtime_exports/`
  - `runtime_sessions/`
  - `.streamlit/secrets.toml`
- Remove tracked `src/__pycache__/*.pyc` files from version control in a cleanup commit. They are already ignored, but currently appear in `git ls-files`.
- Add a short privacy note to `README.md` and `user_documentation.md`: no customer files should be committed; uploads are temporary; reset removes current session data.

Validation:

- `git ls-files data` should show only demo CSVs.
- `git ls-files src/__pycache__` should return nothing after cleanup.
- Upload/runtime directories should not appear in `git status` after a customer upload test.

## Stage 1: Hosted Demo Shell With Access Control

Goal: give remote users a simple hosted entry point without exposing the full prototype or another customer's data.

Recommended first implementation:

- Deploy as a private Streamlit app on a controlled host, not a public unauthenticated link.
- Use a shared demo passcode or simple per-session access token first.
- Store secrets in `.streamlit/secrets.toml` locally and the host's secret manager remotely.
- Add an environment label in the sidebar:
  - `Demo Data`
  - `Customer Upload: <session name>`
  - `Expired / reset required`
- Default remote sessions to `Client Demo Mode`.
- Keep `Full Prototype Mode` available only behind an owner/admin toggle.

Implementation targets:

- `app.py`
  - Replace the current simple demo authentication with a small `auth/session` helper.
  - Display the current active session and data source clearly in the sidebar.
  - Hide raw-data/admin tools from customer users unless they are in an owner/admin mode.
- New helper: `src/session_manager.py`
  - Creates `session_id`.
  - Defines upload, normalized, and export paths.
  - Tracks created-at, last-active, active customer label, and reset state.

Validation:

- Remote user can open the app with a passcode/token.
- Remote user starts in the four-screen client demo flow.
- Owner/admin can still access `Data / Admin` and full prototype features.
- Signing out does not leave imported data visible to the next user.

## Stage 2: Customer Upload Workflow

Goal: let a remote customer upload their own files without asking us to manually place files in the repo's `data/` folder.

User flow:

1. Customer opens the hosted app.
2. Customer selects `Upload Customer Data`.
3. Customer uploads supported files:
   - roster/open-orders workbook
   - candidate tracker CSVs
   - CNC/welder test CSVs
   - intake PDF
4. App saves files under the active `session_id` runtime folder.
5. App runs the existing normalizer against that folder.
6. App shows import diagnostics and staged previews.
7. Customer or owner clicks `Use This Data In Dashboard`.

Implementation targets:

- `src/customer_imports.py`
  - Keep `load_customer_import_preview(data_dir=...)`, but make filename aliases configurable.
  - Add an import manifest that records uploaded filenames, size, modified time, row counts, and parse status.
  - Add redaction-safe diagnostics for display.
- `app.py`
  - Add a clean upload section in `Data / Admin` or a dedicated `Upload Data` page.
  - Use `st.file_uploader(..., accept_multiple_files=True)`.
  - Save uploads only into the current runtime session folder.
  - Allow preview before activation.
  - Add a clear `Use Uploaded Data` button that switches `st.session_state.data_source` to the active session data.
- New helper: `src/import_manifest.py`
  - Writes `manifest.json`.
  - Provides a safe summary for UI.

Validation:

- Uploading the known customer roster/candidate/test/PDF files produces the same or better staged row counts as the current local `data/` preview.
- Missing optional files show warnings, not crashes.
- Wrong file types are rejected.
- Refreshing the browser preserves the active uploaded data for that session.
- A second session cannot see the first session's uploads.

## Stage 3: Reset And Data Purge

Goal: make it impossible for one user's sensitive data to remain visible to the next user.

Reset behavior should clear:

- Uploaded raw files.
- Normalized preview tables.
- Generated exports.
- `st.cache_data`.
- `st.session_state` entries that can contain customer data:
  - `data_source`
  - `worker_overrides`
  - `position_overrides`
  - `worker_notes`
  - `action_statuses`
  - `added_workers`
  - `demo_sent_emails`
  - `demo_sent_sms`
  - any future import/session keys.
- Any uploaded-file references or manifest paths.

Implementation targets:

- `src/session_manager.py`
  - `reset_session(session_id, mode="purge")`.
  - Deletes runtime folder contents for that session.
  - Writes a short reset audit event without storing private values.
- `app.py`
  - Add `Reset This Session` in the sidebar for customer users.
  - Add `Owner Reset All Expired Sessions` for owner/admin users.
  - Require a confirmation checkbox before purge.
  - After reset, return to `Demo Data` and `Client Demo Mode`.

Validation:

- Upload customer files, activate them, then reset.
- Confirm dashboard returns to demo data.
- Confirm staged previews are empty or demo-only.
- Confirm runtime upload/export folders for that session are deleted.
- Confirm a browser refresh after reset does not recover customer data.

## Stage 4: Customer-Centered Data Review

Goal: turn the import screen into a useful customer conversation, not just a table dump.

Focus on the requests they made:

- Active assignments: who is where, when they end, extension/renewal state.
- Open orders: what roles are open, who has been submitted, what needs follow-up.
- Candidate/recruiter process: who is ready, who is missing application/testing/interview/references/profile.
- Intake/timecards: what setup questions are captured and what is still missing.

Implementation targets:

- Improve `Data / Admin -> Customer Imports` into a staged review workflow:
  - `Loaded Sources`
  - `Needs Attention`
  - `Ready To Use`
  - `Missing Fields`
  - `Dashboard Impact`
- Add customer-friendly validation cards:
  - assignments without end dates
  - open orders without client/location/role
  - candidates missing contact fields
  - candidates missing process steps
  - intake/timecard routing questions found
- Add a `Download Import Review` CSV/XLSX bundle for the owner.

Validation:

- Customer can understand what was imported without reading raw CSVs.
- The dashboard clearly explains any missing or uncertain fields before activation.
- No private fields are shown on pages that are visible to unrelated users.

## Stage 5: Session Persistence And Expiration

Goal: support remote customers who reload the page or return shortly after upload, while still avoiding long-lived sensitive storage.

Recommended first policy:

- Default session expiration: 24 hours.
- Owner/admin can purge sooner.
- Expired sessions auto-reset on next access.
- Long-term retention requires an explicit production agreement.

Implementation targets:

- `src/session_manager.py`
  - Store small metadata only: `session_id`, created/updated timestamps, status, data folder paths, row counts.
  - No names, emails, phone numbers, or client details in metadata.
- `app.py`
  - Warn when a session is near expiration.
  - Show `Reset now` and `Download review before reset` options.

Validation:

- Expired session cannot load old uploaded data.
- Non-expired session reloads correctly.
- Metadata has no private customer values.

## Stage 6: Production Data Architecture

Goal: decide what "real" deployment should become after the hosted upload pilot works.

Options:

- Short pilot: runtime file storage only, with automatic purge.
- Internal tool: private database such as PostgreSQL or SQLite on a private VM.
- Customer-owned deployment: each customer gets isolated storage, credentials, backups, and retention policy.
- Integration path: connect to their spreadsheet/ATS/shared drive rather than manual uploads.

Decision needed from the customer:

- Where should the system live long term?
- Who is allowed to upload, view, export, and reset data?
- How long should uploaded data be retained?
- Should notes and workflow updates persist permanently?
- What files are the source of truth?
- Are there compliance, insurance, or contractual data handling requirements?

## Minimal Build Order

1. Repo safety cleanup and ignored runtime directories.
2. `session_manager.py` with session paths and reset.
3. Upload UI that writes to per-session runtime folders.
4. Make `customer_imports.py` consume a session folder instead of only `data/`.
5. Preview, diagnostics, and `Use Uploaded Data`.
6. Reset/purge button with confirmation.
7. Hosted private deployment with secrets.
8. Browser test with two separate sessions to prove isolation.

## First Acceptance Test

Run this before showing the next version to a customer:

1. Start from a clean app session.
2. Confirm the dashboard shows demo data.
3. Upload the customer roster, candidate CSVs, test CSVs, and intake PDF.
4. Confirm staged import counts appear.
5. Activate uploaded data.
6. Confirm Owner Today, Assignment Forecast, Open Orders, and Recruiter Process screens reflect uploaded data.
7. Open a second browser/session and confirm it does not see the first upload.
8. Reset the first session.
9. Refresh the first session and confirm it returns to demo data.
10. Check the runtime folder and confirm uploaded files were removed.

## Open Questions

- Should customers be able to upload data themselves, or should only the owner/admin upload it before a guided review?
- Should remote sessions be anonymous with a passcode, or named per customer/contact?
- Should uploaded data survive for hours, one day, or only until reset/browser close?
- Should the customer be able to download normalized outputs?
- Should candidate contact information be visible in the remote demo, or should phone/email be masked until production permissions are defined?
- Which customer request is highest priority after upload/reset: timecards, open-order follow-up, recruiter process consistency, or assignment renewal forecasting?
